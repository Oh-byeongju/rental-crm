# 자동화 커맨드 생성 가이드

> 새로운 자동화 작업 체계(슬래시 커맨드 + 작업지시서) 를 만들 때 따르는 표준 절차.
> **커맨드별로 작업이 명확하게 이루어지는 것** 이 최우선 목표.

---

## 적용 시점

사용자가 다음을 요청할 때:
- "새 슬래시 커맨드 만들고 싶어"
- "이런 작업을 자동화하자"
- "/{X} 라는 커맨드 만들어줘"

---

## 산출물 구조 — rental-crm 패턴

rental-crm 은 **flat 구조** — ref-project 의 번호 디렉토리(`02. commands/{NNN}. {이름}/`) 와 다르게 파일명만 분리.

```
.claude/commands/
└── {커맨드명}.md              ← 얇은 진입점 (실행 입구)

docs/commands/
└── {커맨드명}-spec.md          ← 두꺼운 spec (절차·규칙·판정 기준)
```

**예시 (현재 등록된 커맨드)**:
```
.claude/commands/cache-refresh.md
docs/commands/cache-refresh-spec.md
```

커맨드가 여러 개면 책임 단위로 분리. spec 폴더는 만들지 않음 — 파일명에 의미를 담는다.

---

## 생성 절차

### 1. 사용자와 대화하며 설계

| 파악 항목 | 질문 예시 |
|---|---|
| **무엇을** 자동화할 것인지 | "어떤 작업을 커맨드로 만들고 싶어?" |
| **몇 단계** 로 나뉘는지 | "이 작업의 사이클은 어떻게 돼?" |
| **입력** 은 무엇인지 | "커맨드에 인자로 뭘 넘길 거야? (없을 수도 있음)" |
| **출력** 은 무엇인지 | "결과물은 파일? 리포트? 코드?" |
| **판정 기준** 이 있는지 | "성공/실패를 어떻게 판단해?" |

### 2. 파일 2개 생성

- `.claude/commands/{커맨드명}.md` — 얇은 진입점 (실행만, 절차는 spec 참조)
- `docs/commands/{커맨드명}-spec.md` — 두꺼운 spec (모든 절차·규칙·판정)

---

## 작업지시서(spec) 작성 원칙

### 원칙 1 — 어느 세션에서 열어도 동일한 결과

- 해석의 여지가 없도록 **모든 단계를 명시**
- glob 패턴, DB 접속 정보, 파라미터 값 등 **리터럴로 고정**
- "알아서 해" 가 아니라 "이 순서대로 이것을 해"

### 원칙 2 — 커맨드 = 하나의 명확한 작업

| 좋은 예 | 나쁜 예 |
|---|---|
| `/cache-refresh` → 캐시 갱신만, 스크립트 수정 X | `/cache-refresh-and-fix` → 캐시 갱신 + 코드 수정 |
| `/domain-spec {도메인}` → 작업지시서 생성만, 코드 X | `/do-everything` → 전부 |

하나의 커맨드는 **하나의 책임**. 여러 작업이면 커맨드 분리.

### 원칙 3 — 에이전트는 지시서를 따르지 해석하지 않음

`.claude/commands/{커맨드명}.md` (얇은 진입점) 에 이렇게 적는다:

```markdown
## 실행

`docs/commands/{커맨드명}-spec.md` 의 절차를
**처음부터 끝까지 그대로** 수행한다.
해석하지 말고 작업지시서에 적힌 그대로 실행한다.
```

### 원칙 4 — 작업지시서의 필수 구성

```markdown
# {작업명} 작업지시서

## 0. 대상 식별
- 인자가 있으면 어떻게 매칭하는지 (glob 패턴 명시)
- 인자가 없으면 어떻게 대상을 결정하는지

## Step 1~N: 실행 단계
- 각 단계별로:
  - 무엇을 하는지 (동사로 시작)
  - 어떤 파일/도구를 사용하는지
  - 판정 기준 (PASS/FAIL/WARN)

## 결과 저장
- 저장 경로 (정확한 패턴)
- 파일 내용 형식 (템플릿)

## 주의사항
- 하지 말아야 할 것 (금지 사항)
- 사용자 승인이 필요한 것
```

---

## 얇은 진입점 — 커맨드 파일 템플릿

```markdown
# {커맨드 설명}

{한 줄 요약. 이 커맨드가 무엇을 하는지.}
**{금지 사항 — 예: 스크립트를 수정하지 않는다}**

## 실행

`docs/commands/{커맨드명}-spec.md` 의 절차를
**처음부터 끝까지 그대로** 수행한다.
해석하지 말고 작업지시서에 적힌 그대로 실행한다.

## 인자

`$ARGUMENTS` — {인자 설명. 없으면 "없음 — {기본 동작}" 명시}

## 순서

1. 작업지시서 읽기
2. Step 1 수행
3. Step N 수행
4. 결과 저장
5. 결과 리포트 출력

{FAIL 시 동작 — 예: 원인 보고 (수정 시도 X)}
```

참고 — 실제 `cache-refresh.md` 가 본 템플릿 그대로 구현되어 있음.

## 다단 사이클 패턴 (LATER 도구 도입 시 참고)

여러 단계로 나뉘는 자동화는 책임 단위로 슬래시 커맨드를 분리.

예: **명세 → 구현 → 검증** 3단

| 단계 | 진입점 (얇은) | 절차 spec (두꺼운) | 산출물 |
|---|---|---|---|
| 명세 | `.claude/commands/domain-spec.md` | `docs/commands/domain-spec-spec.md` | 작업지시서 |
| 구현 | `.claude/commands/domain-build.md` | `docs/commands/domain-build-spec.md` | 코드 |
| 검증 | `.claude/commands/domain-test.md` | `docs/commands/domain-test-spec.md` | 검증 결과 |

각 단계가 **이전 단계의 산출물을 입력으로** 받는다. 사용자 검토 포인트가 단계 사이에 명확히 존재.
