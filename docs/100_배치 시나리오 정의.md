## 1. `BILLING_CREATE` — 월 청구 일괄 생성 (Ch.1 본체)

### 1-1. 개요

매월 1일 새벽 (예: 03:00) 활성 계약 전체에 대해 당월 청구 (`BL_BILLING`) 를 일괄 생성.
**Phase 1 학습 본체** — 건별 INSERT 와 JDBC bulk INSERT 의 성능 차이를 6 라운드로 측정.

### 1-2. 트리거

| 방식 | 호출 |
|---|---|
| 수동 | backoffice `/admin/batch-trigger` → `POST /api/admin/batch-trigger/run/BILLING_CREATE` (이번 달 / 특정 월 인자) |
| 자동 | batch 의 `@Scheduled(cron = "0 0 3 1 * *")` — 매월 1일 03:00 |

### 1-3. 입력

| 인자 | 타입 | 비고 |
|---|---|---|
| `billingMonth` | `YYYY-MM` | 미지정 시 "현재 월" |
| `roundNo` | int (1~6) | 학습용 — 6 라운드 비교 측정. 운영 시점 제거. |

### 1-4. 처리 흐름

```
1. BL_BATCH_LOG INSERT (RUNNING, billingMonth, roundNo)
2. CT_CONTRACT 활성 계약 조회 (status='ACTIVE')
3. 각 계약별:
   - 이미 해당 월 청구 존재? (UNIQUE (CONTRACT_ID, BILLING_MONTH)) → SKIP
   - 청구 INSERT (BL_BILLING.BATCH_LOG_ID = 본 배치 PK 역참조 — 추적성)
   - addProcess(true)
4. (round 별로 INSERT 전략 다름 — §1-6 참조)
5. markCompleted() — durationMs 자동 기록
```

### 1-5. 출력

| 대상 | 내용 |
|---|---|
| `BL_BATCH_LOG` | RUNNING → COMPLETED. `targetCount` (계약 수), `successCount`, `failCount`, `durationMs` |
| `BL_BILLING` | N건 (계약 수만큼) — 각 행 `BATCH_LOG_ID` 로 본 배치 추적 |
| `docs/perf-reports/{YYYY-MM-DD}-billing-create-round{N}.md` | 라운드별 측정 리포트 (Step 7 시점에 형식 확정) |

### 1-6. 6 라운드 측정 계획

| 라운드 | 전략 | 학습 포인트 |
|---|---|---|
| R1 | 건별 `repository.save()` + 매 건 flush | 최악 — 측정 baseline |
| R2 | 건별 `save()` + N건마다 flush + clear | 영속성 컨텍스트 메모리 추세 |
| R3 | JDBC bulk INSERT (`jdbc.batch_size=1000` + `order_inserts=true`) | Hibernate 자동 batching |
| R4 | R3 + chunk commit (1000건마다 트랜잭션 분할) | 트랜잭션 경계 + UNDO 부담 |
| R5 | R4 + UNDO tablespace 작게 강제 → 폭주 재현 | ORA-30036 + 회복 |
| R6 | 멱등성 검증 — 같은 `billingMonth` 재실행 → SKIP 동작 | UNIQUE 제약 + 중복 INSERT 방지 |

> 5만 건 (계약 5만개 가정) 기준. 실 데이터는 시드로 만들거나 sysdate + Random 으로 생성.

### 1-7. 멱등성

- `BL_BILLING(CONTRACT_ID, BILLING_MONTH)` UNIQUE → 중복 호출 시 INSERT 실패 (catch + skip)
- 또는 `MERGE INTO BL_BILLING USING ... ON (...)` (Oracle MERGE) — 학습 비교 대상

## 2. `OVERDUE_UPDATE` — 연체 발생 처리

### 2-1. 개요

매일 새벽 (예: 02:00) 청구 (`BL_BILLING`) 중 납기 초과 + 미납 건을 `BL_OVERDUE` 로 등록 + `BL_BILLING.STATUS = OVERDUE` 갱신.

### 2-2. 트리거

`@Scheduled(cron = "0 0 2 * * *")` 일 단위 + 수동 트리거.

### 2-3. 처리 흐름 (요약)

```
1. BL_BATCH_LOG INSERT (RUNNING)
2. SELECT FROM BL_BILLING WHERE STATUS='UNPAID' AND DUE_DATE < TRUNC(SYSDATE)
3. 각 건:
   - BL_OVERDUE 신규 INSERT (overdue 일수 = SYSDATE - DUE_DATE)
   - BL_BILLING.STATUS = 'OVERDUE'
   - addProcess(true)
4. markCompleted()
```

### 2-4. 학습 포인트

- INSERT (BL_OVERDUE) + UPDATE (BL_BILLING) 혼합 트랜잭션
- 트랜잭션 경계 — 전체 1트랜잭션 vs chunk 별 트랜잭션
- 알림 발생 (`CM_NOTIFICATION` INSERT) 도 같은 트랜잭션에 묶을지 별도로 분리할지

## 3. `KAFKA_PAYMENT_SYNC` — 수납·연체 이벤트 처리 (Ch.3)

### 3-1. 개요

수납 완료 / 연체 발생 시 Kafka 토픽 발행 (Producer) + Consumer 가 연관 도메인 갱신.

### 3-2. 토픽 (이미 인프라 준비됨)

| 토픽 | 발행자 | 소비자 | 페이로드 |
|---|---|---|---|
| `payment.completed` | backoffice (PaymentService.complete) | batch (Consumer → BL_OVERDUE 자동 해제) | paymentId, billingId |
| `payment.overdue`   | batch (OVERDUE_UPDATE) | backoffice (알림 INSERT) | overdueId, customerId, amount |
| `rental.billing.created` | batch (BILLING_CREATE) | backoffice (알림 INSERT) | billingId, customerId |

### 3-3. 학습 포인트

- Producer `acks=all` + `enable.idempotence=true` (이미 yml 설정됨)
- Consumer `manual_immediate` ack (이미 yml 설정됨)
- **Idempotent Consumer** — 처리 결과 키 (예: `paymentId`) 를 Redis 또는 DB 에 기록 + 중복 처리 차단
- offset commit 정책 — 처리 후 commit (at-least-once)

## 4. `OVERDUE_REPORT` — 미납 통계 엑셀 (Ch.2)

### 4-1. 개요

사용자가 `/admin/reports/overdue` 화면에서 "엑셀 다운로드" 버튼 클릭 시 미납 통계 엑셀 (xlsx) 생성.

### 4-2. 배치인가, 동기 응답인가?

**두 갈림길** — Step 8 진행 시 결정:

| 안 | 흐름 | 적합 데이터 |
|---|---|---|
| A. 동기 응답 | 사용자 → backoffice → POI SXSSF 스트리밍 → 즉시 다운로드 | 수만~수십만 행 |
| B. 비동기 배치 | 사용자 → batch 트리거 → 파일 생성 → 알림 → 다운로드 링크 | 수백만 행 / 장시간 |

> 학습 시점에는 A 로 시작 (단순). 데이터가 커져 timeout 위험 시 B 로 전환.

### 4-3. 학습 포인트

- **쿼리 튜닝** — 미납 집계 (서브쿼리 → JOIN) + Oracle EXPLAIN PLAN 전/후 비교
- **인덱스 설계** — `BL_BILLING(STATUS, DUE_DATE)`, `BL_OVERDUE(CUSTOMER_ID)` 활용
- **Apache POI SXSSF** — 행 단위 스트리밍 (메모리 ↓), 워크시트 윈도우 사이즈 100 권장

## 5. `ENERGY_CUSTOMER_SYNC` — 에너지 고객 동기 (학습 확장)

> 가상 시나리오 — 외부 (가스/전기) 사 데이터를 매일 새벽 INSERT.

### 5-1. 개요

매일 새벽 (예: 04:00) 외부 시스템 (가상) 에서 신규/변경 고객을 받아 `CT_CUSTOMER` 동기.

### 5-2. 학습 포인트

- 외부 시스템 → 파일 (CSV) → bulk INSERT
- 멱등성 — 외부 ID 기준 MERGE
- 실패 데이터 분리 (DLQ 패턴 — `BL_BATCH_LOG` 에 fail 건 따로 기록)

---

## 6. `ACCOUNTING_REFRESH` — 회계 정보 갱신 (학습 확장)

### 6-1. 개요

1분 주기로 회계 시스템 (가상 외부) 변경분 polling → 결과를 Redis 캐시에 갱신.

### 6-2. 학습 포인트

- 짧은 주기 스케줄러 — 이전 실행이 안 끝나면 skip (`@Scheduled(fixedDelay)` vs `fixedRate`)
- 분산 환경 락 회피 — ShedLock (Redis) 검토
- 캐시 invalidation — TTL vs 명시적 evict

---

## 7. `STAT_AGGREGATE_DAILY` — 통계 집계 (학습 확장)

### 7-1. 개요

자정 (00:00) 일/주/월 통계 집계 + Redis 캐시 갱신 (대시보드 위젯 응답성).

### 7-2. 집계 대상 (예시)

| 지표 | 출처 | 캐시 키 |
|---|---|---|
| 일별 매출 | `BL_PAYMENT.PAID_AT` 합계 | `stat:revenue:daily:{YYYY-MM-DD}` |
| 미납 건수/금액 | `BL_BILLING WHERE STATUS=UNPAID/OVERDUE` | `stat:overdue:total` |
| 활성 계약 수 | `CT_CONTRACT WHERE STATUS=ACTIVE` | `stat:contract:active` |

### 7-3. 학습 포인트

- 집계 쿼리 (GROUP BY + ROLLUP)
- Redis 키 설계 + TTL
- 대시보드 화면 (`@Scheduled` 직접 vs 본 배치 결과 조회)

## 8. `BL_BATCH_LOG` 컬럼 매핑

본 시나리오들이 모두 같은 테이블에 기록. 학습 진행 중 컬럼 추가 가능.

| 컬럼 | 시나리오별 용도 |
|---|---|
| `BATCH_TYPE` | 위 7개 + 더미 2개 |
| `BILLING_MONTH` | `BILLING_CREATE` / `OVERDUE_REPORT` 만 사용. 나머지 NULL. |
| `TARGET_COUNT` | 처리 대상 건수 (예: 활성 계약 수) |
| `PROCESS_COUNT` / `SUCCESS_COUNT` / `FAIL_COUNT` | 진행 카운터 |
| `DURATION_MS` | 라운드 비교 핵심 |
| `ERROR_MSG` | FAILED 시 |
| `WRK_RMK` | 라운드 번호, chunk size 등 학습 메타정보 |

> **컬럼 추가** (Step 7-A 적용 완료, 2026-05-13):
> - `ROUND_NO NUMBER` — 라운드 비교용 (1~6, 운영 시점 NULL)
> - `BATCH_PARAMS VARCHAR2(500)` — JSON (chunk_size, strategy 등)
> - 같은 작업에서 `CK_BL_BATCH_LOG_TYPE` 제거 (Java 측 `TYPE_*` 상수가 진실) + `UNIQUE (BATCH_TYPE, BILLING_MONTH)` 제거 (같은 month 6 라운드 다건 INSERT 허용 — 멱등성은 Service 측 검증).

## 9. 메뉴 분류 안 (Step 7 시점에 시드 갱신)

`/admin/batch-trigger` 페이지에 **카드 그리드** 로 시나리오 노출. 도메인별 그루핑:

```
[청구]      [BILLING_CREATE]
[연체]      [OVERDUE_UPDATE]
[수납·연체] [KAFKA_PAYMENT_SYNC*]   * = 자동 트리거 (수동 X, 표시만)
[리포트]    [OVERDUE_REPORT]
[외부 동기] [ENERGY_CUSTOMER_SYNC]
[운영]      [ACCOUNTING_REFRESH*] [STAT_AGGREGATE_DAILY]
```

권한 키:
- `BATCH_TRIGGER_VIEW` (현재 시드됨) — 화면 진입
- `BATCH_TRIGGER_EXECUTE` (현재 시드됨) — 모든 시나리오 실행. 후속 분리 검토 (시나리오별 권한)
