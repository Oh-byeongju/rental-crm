## 0. 공통 정의

### 0-1. Base URL

| 환경 | URL |
|---|---|
| 로컬 | `http://localhost:8080` |
| 개발 | TBD |
| 운영 | TBD |

API 경로 prefix:
- 백오피스 / 공용 API: `/api/...`
- 고객 포털 API: `/api/portal/...`

### 0-2. 인증

- 방식: **JWT (Bearer Token)**
- 헤더: `Authorization: Bearer <accessToken>`
- 토큰 종류:
  - Access Token: 30분 만료, 메모리 보관
  - Refresh Token: 7일 만료, Redis 저장 + HttpOnly Cookie (포털)
- 백오피스: 04 §12-2 의 로그인 흐름 따름
- 고객 포털: 04 §12-2 + Refresh Token 회전

**인증 불요 엔드포인트**:
- `POST /api/auth/login`
- `POST /api/portal/auth/register`
- `POST /api/portal/auth/login`
- `POST /api/portal/payments/toss/confirm` (Toss webhook 검증)

### 0-3. 공통 응답 포맷

#### 성공 (2xx)

```json
{
  "code": "SUCCESS",
  "message": "OK",
  "data": { ... }
}
```

#### 페이징 응답

```json
{
  "code": "SUCCESS",
  "message": "OK",
  "data": {
    "content": [ ... ],
    "page": 0,
    "size": 20,
    "totalElements": 153,
    "totalPages": 8,
    "first": true,
    "last": false
  }
}
```

#### 실패 (4xx / 5xx)

```json
{
  "code": "VALIDATION_FAILED",
  "message": "이메일 형식이 올바르지 않습니다",
  "data": null,
  "errors": [
    { "field": "email", "reason": "format" }
  ]
}
```

### 0-4. 에러 코드 체계

| HTTP | code | 의미 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 입력값 검증 실패 |
| 400 | `INVALID_REQUEST` | 잘못된 요청 (포맷·범위) |
| 401 | `UNAUTHORIZED` | 인증 토큰 없음/만료 |
| 401 | `LOGIN_FAILED` | 로그인 실패 (자격 불일치) |
| 401 | `ACCOUNT_LOCKED` | 5회 실패 잠금 |
| 403 | `FORBIDDEN` | 권한 부족 |
| 404 | `NOT_FOUND` | 리소스 없음 |
| 409 | `CONFLICT` | 중복 / 상태 충돌 |
| 409 | `ALREADY_EXISTS` | 동일 식별자 존재 |
| 409 | `BATCH_ALREADY_RUN` | 멱등성 위반 (배치 재실행) |
| 422 | `BUSINESS_RULE` | 비즈니스 규칙 위반 |
| 500 | `INTERNAL_ERROR` | 서버 오류 |
| 503 | `EXTERNAL_SYSTEM_ERROR` | Toss / Kafka 등 외부 시스템 |

### 0-5. 페이징 / 정렬 / 검색 파라미터

| 파라미터 | 타입 | 기본값 | 설명 |
|---|---|---|---|
| `page` | int | 0 | 0-based |
| `size` | int | 20 | 페이지당 건수 (max 100) |
| `sort` | string | (도메인별 기본값) | `필드,asc\|desc` 형식. 다중 sort 가능 |

검색 조건은 엔드포인트별 query parameter 명시.

## 1. 인증 (백오피스)

### 1-1. POST /api/auth/login

**설명**: 백오피스 관리자 로그인

**Request**
```json
{
  "email": "admin@rental.crm",
  "password": "Admin@1234"
}
```

**Response (200)**
```json
{
  "code": "SUCCESS",
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1...",
    "refreshToken": "eyJhbGciOiJIUzI1...",
    "user": {
      "userId": 1,
      "email": "admin@rental.crm",
      "userName": "최고관리자",
      "roleCode": "SUPER_ADMIN"
    }
  }
}
```

**Errors**: `LOGIN_FAILED`, `ACCOUNT_LOCKED`

### 1-2. POST /api/auth/refresh

**Request**: `{ "refreshToken": "..." }`
**Response (200)**: 1-1 의 `accessToken` + `refreshToken` 재발급

### 1-3. POST /api/auth/logout

**Header**: `Authorization: Bearer <accessToken>`
**Response (204)**: Body 없음. Redis 의 refresh token 제거.

## 7. 계약

### 7-1. GET /api/contracts

**Query**: `customerName`, `productName`, `status`, `page`, `size`, `sort`

### 7-2. GET /api/contracts/{contractId}

**Response (200)** — 상세 + 방문 이력 + 청구 이력 요약

### 7-3. POST /api/contracts

**Request**
```json
{
  "customerId": 101,
  "productId": 5,
  "startDate": "2026-06-01",
  "endDate": "2029-05-31",
  "installAddress": "서울시 강남구 ...",
  "monthlyFee": 35000
}
```

**처리 흐름** (04 §4-1):
1. 고객 + 상품 검증
2. 동일 고객 + 동일 상품 ACTIVE 계약 중복 체크 → `CONFLICT`
3. 비활성 상품(`useYn='N'`) 사용 시 → `BUSINESS_RULE`
4. `monthlyFee` 미전송 시 상품 기본값 사용
5. INSERT → contractId 반환

**Response (201)**: `{ "contractId": 1234, "contractNo": "CT-20260601-00001" }`

### 7-4. PUT /api/contracts/{contractId}/suspend

**Request**: `{ "reason": "고객 장기 출장" }`
**처리**: `CONTRACT_STATUS=SUSPENDED`, `SUSPENDED_AT=CURRENT_TIMESTAMP`. 청구 생성 대상에서 제외됨.
**Errors**: `BUSINESS_RULE` (이미 TERMINATED)

### 7-5. PUT /api/contracts/{contractId}/resume

**처리**: `SUSPENDED → ACTIVE`, `RESUMED_AT=CURRENT_TIMESTAMP`

### 7-6. PUT /api/contracts/{contractId}/terminate

**Request**: `{ "reason": "필수 입력" }`
**처리**:
1. `TERMINATE_REASON` 필수 검증 (`VALIDATION_FAILED`)
2. 미납 청구 존재 시 응답에 `unpaidCount` 포함 (확인용)
3. `CONTRACT_STATUS=TERMINATED`, `TERMINATED_AT=CURRENT_TIMESTAMP`
4. 이후 청구 생성 배치에서 제외

## 9. 청구

### 9-1. GET /api/billings

**Query**: `customerName`, `customerId`, `billingMonth`, `status`, `page`, `size`, `sort`

`content` 항목:
```json
{
  "billingId": 5001,
  "billingNo": "BILL-202606-000001",
  "customerId": 101,
  "customerName": "홍길동",
  "contractNo": "CT-20260601-00001",
  "billingMonth": "2026-06",
  "billingAmount": 35000,
  "dueDate": "2026-06-30",
  "billingStatus": "UNPAID",
  "paidAt": null
}
```

### 9-2. GET /api/billings/{billingId}

**Response (200)** — 상세 + 연관 결제 이력 + 연체 정보

### 9-3. POST /api/billings/batch

**설명**: 월 청구 일괄 생성 배치 (관리자 수동 또는 `@Scheduled` 매월 1일)

**Request**
```json
{
  "billingMonth": "2026-06",
  "force": false
}
```

**처리 흐름** (04 §6-1):
1. 멱등성 체크 — `BL_BATCH_LOG` UNIQUE(BATCH_TYPE='BILLING_CREATE', BILLING_MONTH) → `BATCH_ALREADY_RUN`
2. `BL_BATCH_LOG` INSERT (`status=RUNNING`, `startedAt=CURRENT_TIMESTAMP`)
3. 대상 계약 조회 (`CONTRACT_STATUS=ACTIVE` + 해당 청구월 미생성)
4. `BL_BILLING` bulk INSERT (납기일=청구월 말일, 금액=계약 스냅샷)
5. `BL_BATCH_LOG` UPDATE (`status=COMPLETED`, 모든 카운트 + `durationMs`)
6. Kafka 발행: `rental.billing.created`
7. 실패 시 `status=FAILED` + 롤백

**Response (202 Accepted)**
```json
{
  "code": "SUCCESS",
  "data": {
    "batchLogId": 17,
    "targetCount": 12453,
    "successCount": 12453,
    "failCount": 0,
    "durationMs": 8234,
    "status": "COMPLETED"
  }
}
```

**Errors**: `BATCH_ALREADY_RUN` (`force=true` 로 우회 가능, 단 신중)

## 10. 수납

### 10-1. GET /api/payments

**Query**: `customerName`, `paymentMethod`, `paymentDate` (period), `page`

### 10-2. POST /api/payments

**Request**
```json
{
  "billingId": 5001,
  "paymentAmount": 35000,
  "paymentMethod": "BANK",
  "paymentDate": "2026-06-15"
}
```

**처리 흐름** (04 §7-1):
1. 청구 상태 검증 (`UNPAID` / `OVERDUE` 만 허용) → 아니면 `BUSINESS_RULE`
2. 트랜잭션:
   - `BL_PAYMENT` INSERT
   - `BL_BILLING.BILLING_STATUS = PAID`, `PAID_AT = CURRENT_TIMESTAMP`
3. Kafka 발행: `rental.payment.completed`
4. 실패 시 전체 롤백 (5xx)

**규칙**:
- 수납금액 > 0 (`VALIDATION_FAILED`)
- 수납일 ≤ 오늘 (`VALIDATION_FAILED`)

### 10-3. POST /api/payments/{paymentId}/cancel

**Request**: `{ "reason": "필수" }`
**처리**:
1. `PAYMENT_STATUS=CANCELLED`, `CANCELLED_AT`, `CANCEL_REASON` 채움
2. 청구 상태 환원: `BL_BILLING.BILLING_STATUS=UNPAID` (또는 OVERDUE — 납기 기준 재산정)
3. Toss 결제면 Toss API 호출

| PUT | `/api/overdues/{overdueId}/resolve` | 수동 해제 (사유 필수) |

### 11-1. POST /api/overdues/batch

**처리 흐름** (04 §8-1):
1. `BL_BATCH_LOG` INSERT (`BATCH_TYPE=OVERDUE_UPDATE`)
2. `BL_BILLING WHERE STATUS=UNPAID AND DUE_DATE < SYSDATE` 조회
3. `BILLING_STATUS UPDATE → OVERDUE`
4. `BL_OVERDUE` INSERT (한 청구당 1 레코드, ON DUPLICATE 회피)
5. Kafka 발행: `rental.payment.overdue`

### 14-3. 카드 납부 (Toss)

#### POST /api/portal/payments/toss/prepare

**설명**: 결제 사전 준비 (orderId 생성)

**Request**: `{ "billingId": 5001 }`
**Response**: `{ "orderId": "ORDER-2026-XXXXX", "amount": 35000, "customerName": "홍길동" }`

처리:
- `BILLING_STATUS` 검증 (`UNPAID` / `OVERDUE`)
- Redis 에 `payment:lock:{billingId}` SETNX (TTL 10분) — 중복 결제 방지

#### POST /api/portal/payments/toss/confirm

**설명**: Toss 결제 완료 후 검증 (백엔드 검증)

**Request**:
```json
{
  "paymentKey": "...",
  "orderId": "ORDER-2026-XXXXX",
  "amount": 35000
}
```

**처리 흐름** (04 §13-1):
1. Toss 서버 검증 API 호출 (`amount`, `orderId` 일치)
2. 검증 실패 시 → Toss 결제 취소 API 호출 → `EXTERNAL_SYSTEM_ERROR`
3. 트랜잭션:
   - `BL_PAYMENT` INSERT (`PAYMENT_METHOD=TOSS`, `TOSS_ORDER_ID`, `TOSS_PAYMENT_KEY`)
   - `BL_BILLING` UPDATE → `PAID`
4. Kafka 발행: `rental.payment.completed`
5. Redis lock 해제
