## 실수 `mistake`

### 1. 워크트리 잘못 진입 — 인계 노트의 worktree 명시 누락

새 세션 진입 시 `quizzical-dubinsky-0231a8` 워크트리에서 시작. 그러나 153 파일 작업물은 `quirky-mccarthy-c2d6ef` 워크트리에 미커밋 상태로 존재 → quizzical 의 `src/main/java/com/rental/crm/` 에는 5 도메인 + Ch.1/3 도메인 패키지 (billing/payment/overdue/notification 등) 가 **부재**.

**검증 흐름**: `git branch -a` + `git worktree list` + `git log --all` + 파일시스템 grep — 4 워크트리 모두 cb7b80d 동일. 작업 흔적이 어디에도 없는 듯 보였으나, 결국 quirky 의 미커밋(`?? backend/src/main/java/com/rental/crm/billing/` 등 9 패키지) 으로 발견.

**원인**: 이전 세션 종료 시점에 인계 노트 작성하면서 작업한 워크트리 명시 누락. 종료 시 quirky 의 작업물을 커밋도 안 함.

**재발 방지**:
- 인계 노트 첫 줄에 **작업 워크트리 경로** 명시 — 예: "워크트리: `.claude/worktrees/quirky-mccarthy-c2d6ef` (미커밋 153 파일)"
- 종료 직전 `git status` 결과를 인계 노트에 첨부
- 가능하면 종료 직전에 WIP 커밋 (`wip: 세션 종료 — 다음 세션 이어가기용`) 으로 남기기

→ 99 업무현황 메모 섹션에 워크트리 패턴 명시 추가.

### 2. 이전 세션이 cache-refresh 를 quizzical 에서 돌려 quirky 와 시드 차이 발생

quizzical 에서 `infra/init-scripts/oracle/README.md` 메타를 갱신 (인덱스 24→25, 코드값 24→22, 메뉴 23→24). 그러나 quirky 의 `01-create-schema.sql` / `03-seed-codes.sql` 는 더 진화된 상태 (M) — AUTH 57→59, ROLE_AUTH 107→111. quizzical 의 메타 보정은 quirky 기준으로 보면 부정확.

**재발 방지**: README 메타 갱신은 **해당 워크트리의 시드 기준 cache-refresh 후 직접 추출** — 다른 워크트리의 값 차용 금지.

## 잘 작동한 패턴 `pattern`

### 1. Contract 패턴 (7 파일) 그대로 수납에 차용

Contract 의 list + detail 구조 (`list.html` / `detail.html` + `list.js` / `form.js` / `detail.js` + `RestController` / `PageController` = 7 파일) 를 Payment 도메인에 그대로 적용. 모달 패턴 (사유 모달 cancel/refund 공용) 도 동일.

→ **도메인 양산 패턴 안정성 재확인**. 2회차 회고의 "5 도메인 만든 시점에 패턴 충분히 안정" 가설이 3회차에서도 유효.

### 2. X-User-Id 헤더 처리 — App helper 안 건드림

`App.get/put` 은 X-User-Id 미지원. 옵션:
- A) `app.js` 의 `request` 함수에 X-User-Id 자동 추가 → 모든 화면 영향
- B) notification-list.js 안에 별도 `api()` helper 정의 → 영향 0

**결정: B**. 알림은 현재 단계에서 유일하게 X-User-Id 필요한 도메인. JWT 도입 시 인터셉터로 일괄 처리 예정 → 그때 helper 제거. App helper 부작용 회피.

→ 한 도메인만 다른 요구사항일 때 **공통 모듈 수정 vs 도메인별 helper** 선택은 영향 범위로 결정.

### 3. 모달 공용 — pendingAction 분기

Contract detail.js 의 `pendingAction = 'suspend' / 'terminate'` 패턴을 Payment detail.js 에 그대로 (`'cancel' / 'refund'`). 사유 모달 1개로 2 액션 처리.

→ 학습 거리: **UI 컴포넌트 재사용** 패턴. 비슷한 입력 (사유 등) 은 1 모달로.

## 트레이드오프 `tradeoff`

### 1. 인프라 재기동 — `--wait` vs 별도 polling

`docker compose up -d --wait --wait-timeout 540` 한 줄 vs 별도 healthcheck 폴링.

**결정: `--wait`**. 한 명령으로 결과 받음. Oracle start_period 8m 이지만 22초만에 healthy (init 안 됐어도). 결국 그 뒤 USER_TABLES count 별도 확인 + ADR-004 fallback 수행.

→ 사후 평가: `--wait` 가 단순하지만 healthcheck 자체의 정확성 신뢰 불가. **healthy 판정 ≠ init 완료**. 항상 별도 sanity check 필요.

### 2. 수납 7 파일 구성 결정 (인계 노트 vs Contract 패턴 추론)

인계 노트는 "수납 7 파일" 만 명시. 구성은 명시 X.

대안:
- A) list + form + cancel-form + 5 (RestController/PageController/Template/list.js/form.js) = 8 — 너무 많음
- B) list + form + 5 = 5 — 적음
- **C) Contract 패턴 (list + detail 분리, 7 파일) = 7** ✓

**결정: C**. 인계 노트의 7 파일 수치가 Contract 패턴과 일치 — 같은 패턴으로 작성한 것으로 추론. detail 페이지 분리로 cancel/refund 액션 표시.

→ 사후 평가: 패턴 일관성 확보. 단 detail 페이지 분리가 항상 옳은 건 아님 — 단순한 cancel-only 도메인이면 list 안에서 모달로 충분.

## 도구 `tooling`

### 1. ADR-004 fallback — 매번 발생

자동 init 안 됨 → SYSTEM 으로 수동 3 스크립트. `start.bat` 의 로직을 Bash 로 직접 실행. 이 단계가 거의 매번 필요.

→ 학습 거리: **gvenzl/oracle-xe 의 init-scripts 자동 실행 실패 원인 추적**. 현재는 fallback 으로 우회 중. 시간 여유 시 root cause (`ALTER SESSION SET CURRENT_SCHEMA` 동작 차이?) 조사.

### 2. Launch Preview Panel — Thymeleaf 즉시 렌더

template 작성 시 자동 preview. 알림 list.html / 수납 list.html / detail.html 모두 즉시 시각 확인 가능. 모달 / 그리드 / badge / disabled 분기까지.

→ 회고 2회차 평가와 동일: 매우 효과적.

### 3. cache refresh 의 PG → Oracle 변형 시 LONG 타입 회피

ref-project 의 PG 패턴 → rental-crm Oracle 로 변형 시 `USER_TAB_COLUMNS.DATA_DEFAULT` 가 LONG 타입이라 `SUBSTR()` 직접 불가 (ORA-00932). 첫 cache-refresh 에서 발견.

해결:
- A) DATA_DEFAULT 컬럼 제거 ✓
- B) PL/SQL 블록으로 LONG → VARCHAR2 변환
- C) DBMS_METADATA.GET_DDL

**선택: A**. 캐시 용도면 default 값 굳이 필요 X. JPA Entity 의 `@Column(columnDefinition=...)` 보면 됨.

부수 개선: `refresh.py` 에서 returncode != 0 일 때 stdout 끝의 `ORA-*` 라인 추출 — 향후 동종 에러 진단 시간 ↓.

→ **DB 별 메타뷰 특수성** 챙기는 항목. PG → Oracle 차용 시 표준 체크리스트:
- LONG 타입 컬럼 직접 함수 처리 불가
- USER_* vs ALL_* vs DBA_*
- LISTAGG 길이 한계 (Oracle 4000 chars)
