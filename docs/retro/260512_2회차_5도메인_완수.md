## 잘 작동한 패턴 `pattern`

### 1. 도메인 양산 패턴 정형화

장비 / 상품 / 기사 / 방문 모두 **12-15 파일 동일 구조**:
```
{domain}/entity/{Domain}.java
{domain}/repository/{Domain}Repository.java
{domain}/dto/{4 records}
{domain}/service/{Domain}Service.java
{domain}/controller/{Domain}{Rest|Page}Controller.java
templates/{domain}/list.html
static/js/{domain}-{list|form}.js
```

→ 다음 사이클 (Ch.1 청구 / Ch.2 통계 / Ch.3 수납) 도 거의 동일 구조 + 도메인별 특이 사항 (배치 / Kafka).
→ TODO LATER 의 `/domain-spec` `/domain-build` 자동화 도구 도입 시점 명확 (8 도메인 만든 후) 의 근거 — **5 도메인 만든 시점에 패턴 충분히 안정**.

### 2. Service 페이지 단위 매핑 (N+1 회피)

Equipment / Product / Contract / Visit Service 모두 동일 패턴:
```java
Set<Long> fkIds = page.getContent().stream().map(...).collect(toSet());
Map<Long, Other> map = otherRepository.findAllById(fkIds).stream().collect(toMap(...));
return page.map(e -> Response.from(e, map.get(...)));
```

→ JPA fetch join 대신 별도 fetch + Map 매핑. JPQL 단순 + N+1 회피.
→ 향후 `backend/guide/conventions/service-mapping-pattern.md` 룰화 검토 (지금은 코드 4개 중복으로 명확 — 룰화 우선순위 낮음).

### 3. 상태 전이 allow-list (`delete-defense.md` 첫 본격 적용)

계약 (`SUSPENDABLE_STATUS` / `RESUMABLE_STATUS` / `TERMINATABLE_STATUS`) + 방문 (`COMPLETABLE_STATUS` / `CANCELLABLE_STATUS`) + 코드 (`isSystem()`):
```java
public static final Set<String> SUSPENDABLE_STATUS = Set.of(STATUS_ACTIVE);
// Service
if (!Contract.SUSPENDABLE_STATUS.contains(contract.getContractStatus())) {
    throw new BusinessException(ErrorCode.BUSINESS_RULE, "일시정지 불가 상태: " + ...);
}
```

→ Entity 안 상수로 명시 + Service 가 호출 — `delete-defense.md` 룰 의도 그대로.
→ fail-closed (allow 안 되면 거부) — 새 상태 추가 시 자동 차단되어 안전.

### 4. `api-safety.md §2-3` UNIQUE 사전 검증

장비 / 상품 / 계약 / 기사 모든 도메인의 register/update 에 `existsByXxxCode` 사전 검증. UI 친화적 메시지 + DB UNIQUE 위반 회피.

### 5. ref-project 룰 즉시 실전 적용

룰 도입 → 같은 세션에서 4-5 도메인에 즉시 적용. **룰 도입 가치 즉시 실증**.
→ 룰 도입 결정 시 **첫 실전 적용 대상 도메인을 함께 지정** 하면 가치 즉시 측정 가능.

## 도구 `tooling`

### 1. 같은 파일 multi-Edit 안전성 시험 통과

여러 위치 Edit 를 한 응답에 보내도 race condition 발생 안 함 (Claude Code Edit 도구 내부 직렬화 추정).
초기 응답 분산 (위치 1개씩 따로) → 시험 통과 후 **한 응답에 4-6 Edit 묶음** → 작업 속도 약 2배 향상.

### 2. Python 스크립트 일괄 시드 갱신

`03-seed-codes.sql` 의 CM_CODE_GROUP 6 행 + CM_CODE 22 행 갱신 — Edit 도구 30+ 회 대신 임시 `_seed_update.py` 1 회 실행:
- 컬럼 리스트 `.replace()` (모든 INSERT 동일 패턴)
- VALUES `re.subn()` 정규식
- 시스템 그룹 ('Y') vs 일반 그룹 ('N') 분기

작업 효율 ↑↑. 단 정규식 시행착오 2회 (아래 mistake 참조).

### 3. Launch Preview Panel

Template 작성 시 자동 preview — Thymeleaf 렌더 결과를 즉시 시각 확인. 모달 / 그리드 / 상태 badge / disabled 버튼 분기까지.

## 트레이드오프 `tradeoff`

### 1. 코드 구조 강화 — PROP_VAL 개수

ref-project `sy_code_dtl` 는 `cd_prop_val1~5` (5개). rental-crm 도메인 (단순 코드 — 상태/유형/방법) 에는 5개 활용처 명확하지 않음.
**결정: 3개** (PROP_VAL1~3). YAGNI 우선.
→ 사후 평가: 적정. 5개로 갔다면 1-2 개는 영구 미사용 컬럼.

### 2. 계약 자동 채번 — 임시값 UPDATE 패턴

`CT-YYYYMMDD-NNNNN` 생성 위치 결정 — 별도 시퀀스 (Native SQL) vs 임시값 INSERT 후 contractId 받고 UPDATE.
**결정: 임시값 UPDATE** (JPA dirty checking 활용).
```java
Contract draft = Contract.builder().contractNo("TMP-" + System.nanoTime()).build();
Contract saved = contractRepository.save(draft);
saved.assignContractNo(generateContractNo(saved.getContractId()));
```
→ 사후 평가: 단순. 단 INSERT + UPDATE 2회 발생. 대량 등록 시 성능 부담 가능 (학습 단계 OK, 운영 시 별도 시퀀스 검토).

### 3. 재고 모델 — 동적 계산 vs 정적 컬럼

장비 `STOCK_QTY` 만 단일 컬럼. 가용 수량 = `STOCK_QTY - 활성 계약 수` 동적 계산.
**결정: 동적 계산** (정적 `AVAILABLE_QTY` 컬럼 + 차감 로직 X).
→ 사후 평가: 정합성 자연스러움 + 락 불필요. 단 조회마다 native SQL JOIN — Ch.2 쿼리 튜닝 학습 거리.

### 4. 가정한 시그니처 컴파일 미검증 진행

Customer Entity 의 정확한 필드 (`customerNo` / `customerName` / `address`) / `CustomerRepository extends JpaRepository` — Read 안 하고 추측 진행.
**결정: 속도 우선** (Read 추가 시 6 도메인 작업 시간 ↑↑).
→ 사후 평가: **위험**. 컨테이너 미가동 + 컴파일 미검증 상태로 5 도메인 (장비/상품/계약/기사/방문 — Contract Service 가 CustomerRepository 의존) 코드 작성. 가정 오류 시 일괄 수정 필요. 다음 사이클: **첫 도메인 작업 전 ls + 1 Read 로 시그니처 미리 검증**.

## 실수 `mistake`

### 1. Python 시드 갱신 — 정규식 데이터 다양성 누락

첫 시도 패턴: `'[^']*',\s+'[^']*'` (콤마 + `\s+` 공백 1개 이상).

데이터 패턴:
- `'EQUIPMENT_TYPE',  '장비유형'` (공백 2개) — OK
- `'CONTRACT_STATUS', '계약상태'` (공백 1개) — OK
- `'NOTIFICATION_TYPE','알림유형'` (공백 0개) — **매칭 실패**
- `'FURNITURE','가구'` (공백 0개) — **매칭 실패**

**시행착오 2회**:
- 1회: `\s+` → `\s*` (콤마+공백 0 이상). 18건 매칭.
- 2회: 콤마 사이 모두 `\s*` (`'[^']*',\s*'[^']*'`). 1건 추가 매칭 = 19건. 총 22건 OK.

**재발 방지**:
- 정규식 작성 전 데이터 샘플 grep 으로 **공백 변형 / 특수 케이스 미리 확인**
- 패턴 적용 후 매칭 카운트 검증 (`subn` 반환값 활용)

### 2. CONTRACT_RESUME 시드 누락 (ERD-시드 불일치)

ERD CT_CONTRACT 의 상태 전이 — ACTIVE↔SUSPENDED↔TERMINATED 4 전이. 그러나 시드 AUTH 는 SUSPEND/TERMINATE 만 (RESUME 누락).
**원인**: 시드 작성 시점에 상태 전이 4종 정책 명확 X.

→ 작업 중 발견 + Step 0 에서 시드 추가.
**재발 방지**: 새 도메인 작업 시 **상태 전이 매트릭스 먼저 ERD/ADR 확정** → 시드 작성. 작업 중 누락 발견 시 즉시 시드 갱신 + 코드 함께 작성.

### 3. VISIT_CANCEL / VISIT_UPDATE AUTH 누락

방문 도메인 시드에 VISIT_VIEW / VISIT_ASSIGN / VISIT_COMPLETE 만 (CANCEL / UPDATE 누락).
**작업 결정**: VISIT_CANCEL 만 추가 (CANCEL 기능 ERD 명시), VISIT_UPDATE 는 VISIT_ASSIGN 으로 통합 (단순화).
→ 정책상 결정. 운영 시 별도 분리 가능 (TODO LATER 후보).
